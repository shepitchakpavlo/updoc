# 07 — Policy gate

**What to build:** policy-рішення над результатом assessment: 3 критичні поля (ПІБ, номер документа, дата народження) з достатнім confidence + відповідність файла слоту; кожен reject має зрозумілу причину для фідбека працівнику. Невпевнений результат не приймається.

**Blocked by:** 06

**Status:** resolved

- [x] Приймається лише читабельний файл відповідного слота з критичними полями
- [x] Кожен reject має зрозумілу причину (фідбек)
- [x] Невпевнений результат не приймається (рішення Architecture §6)
- [x] Policy не знає про конкретного провайдера (працює над нормалізованим результатом)

## Answer

Реалізовано (apps/api; web не змінювався — контракт feedback той самий):

- **Policy-модуль `apps/api/src/policy/index.ts`** — чиста функція `decidePolicy(expectedSlot, result)` над нормалізованим результатом (контракт `AssessmentResult`) + очікуваним слотом. Порядок перевірок: провайдер відхилив → причина провайдера як feedback; відповідність слота (`recognizedSlot` ≠ очікуваний → причина називає слот); загальний confidence < 0.9 → «невпевнений» (Architecture §6); критичні поля (ПІБ, номер документа, дата народження) — кожне непорожнє і з confidence ≥ 0.9, причина перелічує всі слабкі поля. Решта полів — best-effort, у гейт не входять. Провайдерських імпортів/залежностей немає — лише контракт.
- **Контракт розширено полем `recognizedSlot: BookletSlot | null`** (розпізнаний слот) — Architecture §6 вимагає, щоб виклик оцінював «якість + відповідність слоту + поля», тож policy перевіряє відповідність над результатом, а не довіряє прапорцю провайдера. Метод `assess(file)` не змінився. Формулювання §5 у `Tech/Architecture — UpDoc MVP.md` треба доповнити згадкою про розпізнаний слот — нотатки Obsidian змінюються лише після узгодження з користувачем (AGENTS.md).
- **Мок розширено детермінованим правилом розпізнавання** (той самий файл → той самий результат): файл < 4KB — нечитабельний; далі мок «розпізнає» маркер `mock:slot=<слот>[;uncertain|missing-fields]` у вмісті — без маркера файл «не схожий на сторінки книжечки», з маркером — прийнято з критичними полями (синтетичні значення); модифікатори дають невпевнений/частковий результат — усі гілки policy досяжні в наскрізному ланцюжку для тикета 09.
- **Сервіс `uploadSlot`**: стан визначає policy (`decision.accepted` → «прийнято» / «потрібно перезавантажити»), feedback — причина policy; у БД зберігається нормалізований результат, не рішення. `listByToken` переобчислює feedback через policy зі збереженого assessment (policy — єдиний власник рішень); для старих рядків dev-БД ризику немає — стан needs_reupload міг виникнути лише з `accepted: false`, а такий результат policy пропускає з причиною провайдера як є.

Верифікація: 90 API-тестів (node:test + tsx; нові: 13 тестів policy + 9 тестів мока + 4 тести потоку policy в сервісі) і 17 web-тестів (vitest) — усі зелені; `make typecheck` і `make build` чисті. Селф-рев'ю за skills (code-review, дві осі — Standards/Spec): порушень немає; зауваження-судження враховано (розбіжність §5 — пункт вище; дублювання синтетичних літералів у тестах — свідома конвенція репо; ключі полів як рядки — навмисно, контракт provider-agnostic `Record<string, …>`). Міграцій БД не було (лише типи JSONB). Довготривалі сервіси не запускалися.
